# 05. 最佳实践与使用建议

本章总结了大量实战经验得出的 **"Claude Code 提效方法论"**。按优先级排序，前面的收益最大。

---

## 🥇 原则一：写一份好的 CLAUDE.md

这是**投入产出比最高**的一件事。一份好的 CLAUDE.md 让 Claude 一开始就明白：

- 项目是什么、为什么存在
- 技术栈和架构决策
- 常用命令（build/test/lint）
- **代码约定与禁忌**
- 重要文件的路径

### CLAUDE.md 模板

```markdown
# 项目: <name>

## 它是什么
一句话定位 + 核心业务场景。

## 技术栈
- 语言: TypeScript 5.x
- 运行时: Node 20
- 框架: NestJS 10
- 数据库: PostgreSQL 15 + Prisma
- 包管理器: pnpm（不要用 npm/yarn）

## 目录结构
- src/modules/      业务模块（每个子目录是一个独立领域）
- src/common/       跨模块共用
- src/infra/        基础设施封装（不要在业务里直连 SDK）
- test/             集成测试
- prisma/           数据库 schema

## 常用命令
- pnpm dev          本地启动
- pnpm test         单测（Jest）
- pnpm test:e2e     集成测试
- pnpm lint         lint（ESLint + Prettier）
- pnpm db:migrate   执行迁移

## 代码约定
- 所有异步函数用 async/await，不要用 .then() 链
- 禁止使用 any，必须用具体类型或 unknown
- 新增 API 必须同时写集成测试
- 错误用 AppException 抛出，不要裸 throw Error
- 提交信息遵循 Conventional Commits

## 架构决策记录
- 为什么用 NestJS：DI + 模块化，团队熟悉
- 为什么不用 GraphQL：内部系统，REST 足够
- 为什么 Prisma 不用 TypeORM：类型体验更好

## 禁区（AI 不要改）
- src/infra/payment/**  支付相关必须人工修改
- prisma/migrations/**  已执行的迁移只增不改
```

### 维护建议

- 每次大的架构变动后更新
- 定期让 Claude 自己 review：`请检查 CLAUDE.md，是否和当前代码现状一致？`
- 不要写太长，**超过 500 行说明你该拆分了**（用子目录的 CLAUDE.md）

## 🥈 原则二：任务分阶段，小步快跑

### ❌ 反例

```text
帮我把这个 JS 项目迁移到 TS，顺便升级依赖、加测试覆盖率。
```

这是灾难。Claude 会改上百个文件，你无法 review。

### ✅ 正例

```text
我们要做一个大迁移，分阶段进行。今天只做第 1 阶段：

【阶段 1】改造构建配置
1. 安装 typescript 和相关依赖
2. 加 tsconfig.json（strict 关闭，先跑通）
3. 改 package.json scripts
4. 不要改任何 .js 文件

做完后运行 pnpm build，确认能通过。等我审阅后再开始阶段 2。
```

**每个阶段都有：明确范围、明确产出、明确验证方式。**

## 🥉 原则三：让它"先读后写"

Claude 擅长写代码，但**更擅长的是先理解再动手**。养成这个模板：

```text
【任务】<一句话描述>

【请先做】
1. 阅读 @src/xxx 和 @src/yyy
2. 给我一个 100 字的现状描述
3. 给我 2~3 个可选方案，说明优劣
4. 等我选定方案后再写代码
```

这能显著降低"AI 自信地跑偏"的概率。

---

## 原则四：Prompt 里加"约束"

相比于告诉它要做什么，**告诉它不要做什么**往往更有效：

✅ 好约束：
- "只改 `src/auth/` 下的文件，其他文件一行都不要动"
- "不要新增任何依赖，用现有库实现"
- "不要改测试，先让代码通过现有测试"
- "回答不超过 300 字"
- "不要道歉、不要客套，直接给方案"

---

## 原则五：善用 `/clear` 与 `/compact`

**会话越长，Claude 越容易：**
- 忘记早期指令
- 被历史误导（比如前面讨论过但后来方向变了）
- 消耗过多 token

### 策略

- **一个会话只做一类任务**：重构归重构，写文档归写文档。切换时 `/clear`。
- **超过 30 轮对话** → 考虑 `/compact`。
- **任务完成但还想继续** → 先让它总结，再 `/clear`，把总结贴回去开新话题。

---

## 原则六：用「对抗式提问」验证它

让 Claude 改完后，不要直接相信，**用它自己挑它自己的刺**：

```text
你刚才写的方案有哪些潜在问题？列出 3 个最可能出错的场景。
```

```text
假设你是一个对这段代码不满意的 code reviewer，你会提什么意见？
```

```text
如果这段代码上线后出现 bug，最可能的 3 个原因是什么？
```

这种元认知提问往往能让 Claude 自己发现问题。

---

## 原则七：用"对话日志"作为记忆

Claude Code 本身不持久化记忆，但你可以：

1. 每个重要会话结束前让它生成 `docs/dev-log/YYYY-MM-DD-<topic>.md`
2. 内容包含：做了什么、为什么、有什么未决问题
3. 下次相关任务前让它 `@docs/dev-log/` 读最新几篇

这比依赖长对话更可靠。

---

## 原则八：模型切换策略

| 任务类型 | 推荐模型 |
| --- | --- |
| 日常改代码、写测试、回答问题 | Sonnet（默认） |
| 复杂架构设计、疑难 bug、跨 10+ 文件重构 | Opus |
| 批量简单任务（改格式、重命名） | Haiku（省钱） |

切换：`/model`，或在配置里设默认值。

**省钱建议**：日常用 Sonnet，卡住时再 `/model` 切 Opus 问同一个问题。

---

## 原则九：权限从严

新项目第一天就配好 `deny` 列表。推荐最小禁用集：

```json
{
  "permissions": {
    "deny": [
      "Bash(rm -rf:*)",
      "Bash(sudo:*)",
      "Bash(curl * | sh*)",
      "Bash(wget * | sh*)",
      "Read(.env*)",
      "Read(**/*.pem)",
      "Read(**/id_rsa*)",
      "Edit(.env*)",
      "Edit(**/credentials*)"
    ]
  }
}
```

## 原则十：敬畏生产、敬畏安全

**永远不要让 Claude 直接操作生产环境。** 即使在本地也要：

- 先 `git add -p` 自己审阅每一处改动
- 重要改动提交前跑完整测试
- 数据库迁移必须人工 review
- 涉及钱、身份、权限的代码，AI 只能辅助不能主导

**一个经验法则**：如果这段代码出 bug 你会被老板请喝茶，就不要让 AI 独立完成。

---

## 常见反模式（避免）

| 反模式 | 问题 | 正确姿势 |
| --- | --- | --- |
| 用中文描述需求但项目是英文注释 | 风格不一致 | 在 CLAUDE.md 里约定语言 |
| 一次性丢 10 个需求 | 难以 review | 拆成 10 个会话或分阶段 |
| 把 API Key 贴在对话里让它调试 | 泄漏风险 | 用环境变量，教它读 env 名字 |
| 相信它说的"已经跑过测试" | 可能没跑 | 让它粘贴完整测试输出 |
| 复杂 bug 直接问"怎么修" | 药不对症 | 先让它分析根因，再选方案 |
