# 01 — 容器技术基础与 Docker 核心概念

> 在学任何命令之前，先搞懂"容器到底是个什么东西"

---

## 一、为什么需要容器？

### 1.1 传统部署的痛点

想象你是一个厨师，你在自己家厨房做了一道菜，味道很棒。现在老板让你去另一个厨房做同样的菜，但是——

- 那个厨房的锅不一样
- 调料品牌不同
- 灶台火力不同
- 甚至连水都不一样

结果？同样的菜谱，做出来味道完全不同。

**这就是软件部署的经典问题：**

```
开发者：在我电脑上明明跑得好好的啊！
运维：那你把你的电脑搬过来吧……
```

具体来说，传统部署面临这些痛点：

| 问题 | 表现 |
|-----|------|
| 环境不一致 | 开发、测试、生产环境不同，导致各种奇怪 Bug |
| 依赖冲突 | 项目 A 需要 Python 3.8，项目 B 需要 Python 3.11 |
| 部署复杂 | 装系统、配环境、装依赖、改配置，一套流程几小时 |
| 资源浪费 | 一台服务器只跑一个应用，CPU 和内存大量闲置 |
| 扩缩容慢 | 流量突增时，新开服务器+部署应用要几十分钟 |

### 1.2 虚拟机：第一代解决方案

为了解决环境隔离问题，人们发明了**虚拟机（VM）**。

**虚拟机的原理**：在物理机上模拟出多个完整的计算机，每个都有自己的操作系统。

```
┌─────────────────────────────────────┐
│          物理服务器（宿主机）           │
│  ┌─────────┐ ┌─────────┐ ┌────────┐ │
│  │  VM-1   │ │  VM-2   │ │ VM-3   │ │
│  │  App A  │ │  App B  │ │ App C  │ │
│  │  依赖库  │ │  依赖库  │ │ 依赖库  │ │
│  │ Ubuntu  │ │ CentOS  │ │ Debian │ │
│  └─────────┘ └─────────┘ └────────┘ │
│        Hypervisor（虚拟化层）          │
│           宿主机操作系统               │
│             硬件                      │
└─────────────────────────────────────┘
```

**虚拟机的问题**：
- **太重了**：每个 VM 都要装一个完整操作系统（几 GB）
- **启动慢**：开一个 VM 要几分钟，跟开电脑一样
- **资源浪费**：每个 VM 的操作系统本身就吃内存和 CPU
- **数量有限**：一台物理机最多跑十几个 VM

> 类比：虚拟机就像你为了做不同的菜，租了好几个完整的厨房，每个厨房都有独立的水电煤气。虽然彻底隔离了，但成本太高。

### 1.3 容器：更优雅的答案

**容器的思路**：不需要模拟整个操作系统，只需要把应用和它的依赖打包在一起，共享宿主机的操作系统内核。

```
┌─────────────────────────────────────┐
│          物理服务器（宿主机）           │
│  ┌─────────┐ ┌─────────┐ ┌────────┐ │
│  │容器-1   │ │容器-2   │ │容器-3  │ │
│  │  App A  │ │  App B  │ │ App C  │ │
│  │  依赖库  │ │  依赖库  │ │ 依赖库  │ │
│  └─────────┘ └─────────┘ └────────┘ │
│         Docker Engine（容器引擎）      │
│           宿主机操作系统               │
│             硬件                      │
└─────────────────────────────────────┘
```

> 类比：容器就像同一个厨房里的不同工作台。共享水电煤气（操作系统内核），但每个工作台有自己的刀具、调料、案板（依赖和文件系统），互不干扰。

### 1.4 虚拟机 vs 容器 对比

| 特性 | 虚拟机 | 容器 |
|-----|-------|------|
| 隔离级别 | 完整操作系统隔离 | 进程级隔离 |
| 启动速度 | 分钟级 | **秒级甚至毫秒级** |
| 体积大小 | GB 级 | **MB 级** |
| 性能损耗 | 5-15% | **接近零** |
| 单机运行数量 | 十几个 | **成百上千个** |
| 资源利用率 | 较低 | **非常高** |
| 安全隔离 | 强（硬件级） | 较弱（内核共享） |

**结论**：容器不是替代虚拟机，而是互补。对于大多数应用部署场景，容器更轻量、更高效。

## 二、容器的底层原理（Linux 基础）

容器不是凭空变出来的魔法，它依赖 Linux 内核的三大核心技术：

### 2.1 Namespace — 隔离术

Namespace 让每个容器以为自己独占一台机器。

```
┌──────────────────────────────────────┐
│ Linux 内核                            │
│                                      │
│  PID Namespace  → 每个容器有独立的进程号  │
│  NET Namespace  → 每个容器有独立的网络栈  │
│  MNT Namespace  → 每个容器有独立的文件系统 │
│  UTS Namespace  → 每个容器有独立的主机名  │
│  IPC Namespace  → 每个容器有独立的进程通信 │
│  USER Namespace → 每个容器有独立的用户    │
└──────────────────────────────────────┘
```

**通俗理解**：就像戴了 VR 眼镜，每个容器看到的都是自己的"虚拟世界"，但实际上大家都在同一个房间里。

### 2.2 Cgroups — 资源管控

Cgroups（Control Groups）负责限制每个容器能用多少资源。

```bash
# 限制容器只能用 1 个 CPU 核心和 512MB 内存
docker run --cpus=1 --memory=512m nginx
```

**通俗理解**：Namespace 是"隔离"，Cgroups 是"限额"。就像自助餐厅，虽然大家在同一个餐厅（共享内核），但每人有一个限量的盘子（资源配额）。

### 2.3 Union FS — 分层文件系统

Union File System（联合文件系统）让镜像可以分层存储，大幅节省空间。

```
┌────────────────────────┐
│  容器层（可写）          │ ← 你在容器里改的东西在这层
├────────────────────────┤
│  应用层（只读）          │ ← 你的应用代码
├────────────────────────┤
│  依赖层（只读）          │ ← pip install 的包
├────────────────────────┤
│  基础镜像层（只读）      │ ← Ubuntu / Alpine 等
└────────────────────────┘
```

**通俗理解**：像千层蛋糕一样，每一层都是只读的，你只能在最上面加一层奶油（可写层）。多个容器可以共享底下的蛋糕层，只是各自有不同的奶油层。

## 三、Docker 是什么？

### 3.1 Docker 的定义

**Docker** 是目前最流行的容器引擎，它让你可以：

1. **打包**：把应用和所有依赖打成一个"镜像"（Image）
2. **分发**：把镜像推送到仓库，任何人都能下载
3. **运行**：一条命令启动容器，秒级部署

```
Docker = 打包工具 + 运行时 + 分发平台
```

### 3.2 Docker 的核心架构

```
┌──────────────────────────────────────────────┐
│                  Docker 架构                   │
│                                              │
│  ┌─────────┐    ┌──────────────────────────┐ │
│  │ Docker   │    │     Docker Daemon        │ │
│  │ Client   │───▶│     (dockerd)            │ │
│  │ (命令行)  │    │                          │ │
│  └─────────┘    │  ┌────────┐ ┌─────────┐  │ │
│                  │  │ Images │ │Containers│  │ │
│  docker run     │  └────────┘ └─────────┘  │ │
│  docker build   │  ┌────────┐ ┌─────────┐  │ │
│  docker pull    │  │Networks│ │ Volumes  │  │ │
│  ...            │  └────────┘ └─────────┘  │ │
│                  └──────────────────────────┘ │
│                          │                    │
│                          ▼                    │
│                  ┌──────────────┐             │
│                  │   Registry   │             │
│                  │ (镜像仓库)    │             │
│                  │ Docker Hub   │             │
│                  │ 私有仓库      │             │
│                  └──────────────┘             │
└──────────────────────────────────────────────┘
```

三大核心角色：

| 角色 | 说明 | 类比 |
|-----|------|------|
| **Docker Client** | 你敲的命令行工具 | 你在手机上点"下单" |
| **Docker Daemon** | 后台常驻服务，真正干活的 | 厨房里的厨师 |
| **Registry** | 镜像仓库，存放镜像的地方 | 菜谱图书馆 |

### 3.3 Docker 的核心概念

#### 镜像（Image）— 只读模板

- **是什么**：一个只读的文件包，包含运行应用所需的一切（代码、运行时、库、配置）
- **类比**：就像一个"装机光盘"，或者"菜谱+食材包"
- **特点**：只读、分层、可共享

```bash
# 查看本地有哪些镜像
docker images

# 输出示例
REPOSITORY    TAG       IMAGE ID       CREATED        SIZE
nginx         latest    a8758716bb6a   2 days ago     187MB
python        3.11      d4b7e1c27c14   1 week ago     1.01GB
alpine        latest    05455a08881e   2 weeks ago    7.38MB
```

#### 容器（Container）— 运行实例

- **是什么**：镜像的运行实例，就是一个被隔离的进程
- **类比**：镜像是"菜谱+食材包"，容器是"按菜谱做出来的那道菜"
- **特点**：可创建、启动、停止、删除、暂停

```bash
# 用 nginx 镜像创建并运行一个容器
docker run -d --name my-web -p 80:80 nginx
```

#### 仓库（Registry）— 镜像商店

- **是什么**：集中存放镜像的服务
- **Docker Hub**：官方公共仓库（类似 GitHub）
- **私有仓库**：企业内部使用（Harbor、阿里云 ACR 等）

```bash
# 从 Docker Hub 拉取镜像
docker pull nginx:latest

# 推送镜像到仓库
docker push myuser/myapp:v1.0
```

### 3.4 一图理解 Docker 工作流

```
                    ┌─────────────┐
                    │  Dockerfile │
                    │  (构建蓝图)  │
                    └──────┬──────┘
                           │ docker build
                           ▼
┌──────────┐       ┌──────────────┐       ┌──────────────┐
│ Registry │◀─────▶│    Image     │──────▶│  Container   │
│ (仓库)   │ push  │   (镜像)     │  run  │   (容器)     │
│          │ pull  │              │       │              │
└──────────┘       └──────────────┘       └──────────────┘
                                                 │
                                          start / stop
                                          restart / rm
```

**完整流程**：
1. 编写 **Dockerfile**（构建蓝图）
2. `docker build` → 生成 **镜像**
3. `docker push` → 推送到 **仓库**（分享给别人）
4. `docker pull` → 从仓库拉取镜像
5. `docker run` → 用镜像创建并运行 **容器**

## 四、Docker vs 其他容器技术

Docker 不是唯一的容器方案，了解一下生态全貌：

### 4.1 容器技术发展时间线

```
2008  LXC 诞生（Linux Containers，容器鼻祖）
  │
2013  Docker 诞生（封装 LXC，让容器变得简单好用）
  │
2015  OCI 标准建立（开放容器标准，避免一家独大）
  │     ├── 镜像规范（Image Spec）
  │     └── 运行时规范（Runtime Spec）
  │
2016  containerd 从 Docker 剥离出来
  │
2017  CRI-O 诞生（专为 Kubernetes 设计的容器运行时）
  │
2020  nerdctl 诞生（containerd 的命令行工具）
  │
2022  Kubernetes 正式移除 dockershim
  │
现在   containerd + nerdctl 成为新趋势
```

### 4.2 核心组件关系

```
┌────────────────────────────────────────┐
│            用户命令行界面                 │
│   docker CLI  │  nerdctl  │  crictl    │
├────────────────────────────────────────┤
│           容器管理层                     │
│   dockerd     │  containerd            │
├────────────────────────────────────────┤
│           OCI 运行时                    │
│              runc                      │
├────────────────────────────────────────┤
│           Linux 内核                    │
│   Namespace │ Cgroups │ Union FS       │
└────────────────────────────────────────┘
```

| 组件 | 角色 | 一句话说明 |
|------|------|----------|
| **docker CLI** | 命令行 | 你敲的 `docker xxx` 命令 |
| **dockerd** | 守护进程 | Docker 的大管家，管镜像、容器、网络、存储 |
| **containerd** | 容器运行时 | 真正管理容器生命周期的核心组件 |
| **runc** | OCI 运行时 | 最底层的容器创建工具，直接调用内核 |
| **nerdctl** | 命令行 | containerd 的命令行，Docker CLI 的替代品 |

**重点理解**：Docker 其实是一层"包装"。真正干活的是 containerd 和 runc。Docker 的贡献在于让容器技术变得简单好用，而不是发明了容器技术本身。

## 五、为什么要学 nerdctl？

### 5.1 Kubernetes 已不再依赖 Docker

```
Kubernetes 1.24 之前：
  K8s → dockershim → Docker → containerd → runc

Kubernetes 1.24 之后：
  K8s → CRI → containerd → runc
        （直接对接 containerd，绕过了 Docker）
```

这意味着：
- 在 K8s 节点上，可能根本没有安装 Docker
- 但 containerd 一定在
- **nerdctl** 就是为了在这种环境下管理容器而生的

### 5.2 nerdctl 的优势

| 优势 | 说明 |
|------|------|
| 命令兼容 | 语法和 Docker 几乎一模一样，学习成本为零 |
| 更轻量 | 不需要 dockerd，直接和 containerd 通信 |
| 原生支持 | 和 K8s 使用同一个容器运行时，没有兼容问题 |
| 新特性 | 支持 lazy-pulling、加密镜像等 Docker 没有的功能 |

```bash
# Docker 命令
docker run -d --name web -p 80:80 nginx

# nerdctl 命令（几乎一样）
nerdctl run -d --name web -p 80:80 nginx
```

## 六、本章小结

### 核心知识点回顾

```
✅ 容器解决的问题：环境不一致、部署复杂、资源浪费
✅ 容器 vs 虚拟机：更轻、更快、更省资源
✅ 容器三大底层技术：Namespace（隔离）、Cgroups（限额）、Union FS（分层）
✅ Docker 三大核心：镜像（模板）、容器（实例）、仓库（商店）
✅ Docker 架构：Client → Daemon → Registry
✅ 容器生态：Docker → containerd → runc → nerdctl
✅ 为什么学 nerdctl：K8s 趋势，更轻量，命令兼容
```
